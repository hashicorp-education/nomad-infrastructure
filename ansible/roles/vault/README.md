# Vault Role

## Description

The vault role installs and configures a self-hosted HashiCorp Vault server
using Raft integrated storage. It handles binary installation, configuration
file generation, systemd service setup, and initial service startup. It does
**not** initialize or unseal Vault — see [ansible/playbooks/vault_servers.yaml](../../playbooks/vault_servers.yaml)
for that.

## Features

- Installs the Vault binary via the `hashicorp_release` role
- Creates configuration and data directories
- Generates `vault.hcl` from a Jinja2 template using Raft integrated storage
  (no external storage backend and no Consul dependency)
- Sets up a systemd service for automatic startup
- Supports TLS using the same shared self-signed CA already generated by the
  `tls` role for Nomad and Consul
- Supports AWS cloud auto-join or a static Raft `retry_join` list built from
  the `servers` inventory group (same fallback pattern as the `nomad`/`consul`
  roles)
- Runs `vault operator diagnose` against the rendered config (tag `vault_validate`)
  before notifying a restart, informational only (`failed_when: false`)

## Variables

| Variable | Type | Default | Description |
|----------|------|---------|-------------|
| `vault_user` | string | `root` | User to run the Vault service |
| `vault_group` | string | `root` | Group to run the Vault service |
| `vault_binary_version` | string | `1.20.1` | Vault version to install |
| `vault_node_name` | string | `{{ inventory_hostname }}` | Raft `node_id`; `vault_servers.yaml` overrides this to `vault-server-N` |

| `vault_service_name` | string | `vault` | Systemd service name |

| `vault_cluster_port` | int | `8201` | Raft cluster listener port |
| `vault_ui_enabled` | bool | `true` | Enable the Vault web UI |

| `vault_tls_enabled` | bool | `true` | Enable TLS for the HTTP API and cluster listener |

| `vault_cloud_auto_join_tag_value` | string | `server` | AWS tag value for auto-join |

## Directory structure

The role creates the following directories:
```
/etc/vault.d/           # Configuration files (and .tls/ certs, copied by vault_servers.yaml)
/opt/vault/data/        # Raft integrated storage
```

## TLS

Reuses the shared cluster CA (`ansible/.tls/ca.pem`) generated by the `tls`
role. `vault_servers.yaml` copies the per-host cert/key already generated for
that node (the same cert used for Nomad and Consul on that host) to
`/etc/vault.d/.tls/vault.crt` and `/etc/vault.d/.tls/vault.key`.

## Security notes (intentional simplifications)

This role follows the same pragmatic trade-offs already documented elsewhere
in this repo (self-signed certs, ACLs disabled by default, etc.) rather than
Vault's official hardening guide:

- **Runs as `root`**, matching this repo's existing Nomad/Consul convention —
  not Vault's recommended dedicated non-root user + `CAP_IPC_LOCK`. Running
  as root allows Vault to `mlock()` memory (preventing secrets from swapping
  to disk) without extra systemd capabilities.
- **Single unseal key share** (`-key-shares=1 -key-threshold=1`, set by
  `vault_servers.yaml`) instead of Shamir's default 5-of-3, and no
  auto-unseal/KMS integration. Do not reuse this initialization pattern for a
  production Vault cluster.
- **`disable_mlock = false`** (`vault_disable_mlock` default) — Vault 1.20+
  requires this set explicitly or `vault.service` fails to start
  (`disable_mlock must be configured 'true' or 'false'`). Kept `false`
  specifically because this role runs Vault as root (above), which is what
  lets `mlock()` succeed without granting `CAP_IPC_LOCK`.

## Example usage

```yaml
- role: vault
  vars:
    vault_node_name: "vault-server-1"
    vault_tls_enabled: true
```

See [ansible/playbooks/vault_servers.yaml](../../playbooks/vault_servers.yaml)
for the full play, including TLS cert distribution and cluster
initialization/unseal.
