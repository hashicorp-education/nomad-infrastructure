# Plan: Local Mac testing with Terraform + Multipass

**Status: Proposal, not implemented.**

Goal: let a developer on an Apple Silicon Mac stand up the same Nomad (+
optionally Consul/Vault) cluster this repo builds on AWS, but on local
Multipass VMs instead of EC2 instances, then run the existing Ansible
`deploy_*.yaml` scenarios against it unmodified (or nearly unmodified).

Decisions locked in for this plan (confirmed with the user):

| Decision | Choice |
|----------|--------|
| Terraform workspace | New `terraform/multipass/`, sibling to `terraform/aws/`. Independent state — does not touch `terraform/aws/terraform.tfstate`. |
| Terraform provider | [`larstobi/multipass`](https://registry.terraform.io/providers/larstobi/multipass/latest/docs) — published on the public Registry, so plain `terraform init` works, no dev overrides |
| Ansible inventory | New `ansible/inventory.multipass.ini` (generated by Terraform). Coexists with `ansible/inventory.ini` (AWS) — never overwritten, switch between them with `-i` |
| Cluster topology | Same as AWS default: 3 servers + 2 clients (5 VMs total) |
| Per-VM resources | 2 CPUs / 4GB RAM / **10GB disk** (reduced from an initial 20GB proposal — local disk space is constrained) |
| VM image | Ubuntu 24.04 (noble) — matches the AWS AMI (`ubuntu-noble-24.04-amd64-server-*`; Multipass will select the arm64 build automatically on Apple Silicon) |
| SSH key | **Reuse the user's existing key**, `~/.ssh/id_ed25519` / `~/.ssh/id_ed25519.pub` — no new Terraform-generated keypair (unlike AWS's `keypair.tf`, which generates one because EC2 key pairs are a first-class AWS object. Multipass has no such object; cloud-init is the only injection point, so reusing an existing key is simpler and avoids a second key file to manage) |
| First validation scenario | **Scenario C** — `deploy_consul_nomad_sd.yaml` (Consul + Nomad + service discovery) — changed from an initial Scenario B (Nomad-only) proposal once the user confirmed Consul is needed for service discovery |

## 0. Why this is additive, not a rewrite

Before proposing new code, the existing Ansible layer was checked for
AWS-specific assumptions. Most of it is already cloud-agnostic:

- **`hashicorp_release` role** (installs Nomad/Consul/Vault) and the **`cni`
  role** already map `ansible_facts['architecture']` (`aarch64` → `arm64`,
  `x86_64` → `amd64`) into the correct download URL. Apple Silicon Multipass
  VMs run arm64 Ubuntu images — both roles will pull the correct binaries
  with **no code changes**.
- **`nomad` role's `retry_join`** already falls back to a static list built
  from each host's own `ansible_facts.default_ipv4.address` whenever
  `nomad_cloud_auto_join_enabled: false` — which is already the value both
  `nomad_servers.yaml` and `nomad_clients.yaml` pass today. Nomad clustering
  has **no AWS dependency today** and needs no change.
- **`tls` role** only uses `IP:{{ ansible_host }}` (+ `IP:127.0.0.1`) for
  certificate SANs — no `private_ip`/AWS hostvar dependency.
- **`ansible_user=ubuntu`** (set in `[all:vars]` of every inventory) matches
  Multipass's default Ubuntu cloud-image user.
- **`common_setup.yaml`** only manages sudoers and pings hosts — no AWS
  metadata/API calls.

**The one real gap (now fixed):** `ansible/playbooks/consul_servers.yaml`,
`consul_clients.yaml`, and `consul_dns_token.yaml` hardcoded
`consul_cloud_auto_join_enabled: true`, which renders `retry_join =
["provider=aws tag_key=... tag_value=..."]` — this requires the AWS EC2 API
and IAM permissions that don't exist locally. The `consul` role's template
already has the same static-IP fallback pattern as Nomad's, so the fix was to
make the hardcoded value overridable, not to add new logic:

```yaml
# was: consul_cloud_auto_join_enabled: true
consul_cloud_auto_join_enabled: "{{ consul_use_aws_cloud_join | default(true) }}"
```

`consul_use_aws_cloud_join` is a new, never-otherwise-set variable name, so
`default(true)` preserves AWS behavior exactly. `ansible/inventory.multipass.ini`
will set `consul_use_aws_cloud_join=false` in `[all:vars]` once created (§1),
falling back to the role's static-IP retry_join. **Status: applied** to all
three files — regression-checked with `--syntax-check` against every AWS
entrypoint that imports them (`deploy_consul.yaml`,
`deploy_consul_nomad_sd.yaml`, `deploy_consul_nomad_wi.yaml`) with no changes
in behavior since `consul_use_aws_cloud_join` is undefined for AWS runs today.

`ansible/playbooks/consul_nomad_service_mesh.yaml` (Option E only, not needed
for Scenario C) still hardcodes `true` in two places and was intentionally
left unchanged — apply the same fix there if Option E is needed locally later.

Because Scenario C (`deploy_consul_nomad_sd.yaml`) is the user's chosen first
validation target, this fix is required for **Phase 1**, not deferred to an
optional later phase as originally scoped.

## 1. New Terraform workspace: `terraform/multipass/`

Mirrors `terraform/aws/`'s file layout where it makes sense:

| File | Purpose |
|------|---------|
| `main.tf` | `required_providers { multipass = { source = "larstobi/multipass", version = "~> 1.4" } }` |
| `variables.tf` | `server_count` (default 3), `client_count` (default 2), `vm_cpus` (default 2), `vm_memory` (default `"4GiB"`), `vm_disk` (default `"10GiB"`), `vm_image` (default `"24.04"`), `ssh_public_key_path` (default `~/.ssh/id_ed25519.pub`), `ssh_private_key_path` (default `~/.ssh/id_ed25519`), `project_name` (default `nomad-consul-local`) |
| `cloudinit.yaml.tpl` | `templatefile()`'d cloud-init user-data: appends the user's public key to the `ubuntu` user's `ssh_authorized_keys` (top-level `ssh_authorized_keys:` list — additive, doesn't redefine the `users:` block that Multipass's own image already sets up) |
| `compute.tf` | `multipass_instance.servers` (count = `var.server_count`) and `multipass_instance.clients` (count = `var.client_count`), each with `cpus`, `memory`, `disk`, `image = var.vm_image`, `cloudinit_file = local_file.cloudinit.filename` |
| `inventory.tpl` | Same shape as `terraform/aws/inventory.tpl`, but `private_ip` is set to the same value as the instance's `ipv4` output (Multipass has no public/private split — one NIC on the shared bridge network) |
| `outputs.tf` | Server/client names + `ipv4` addresses, for convenience (`terraform output`) |
| `terraform.tfvars.example` | Documents all overridable variables |
| `README.md` | Prereqs (Multipass installed via `brew install --cask multipass`), usage, teardown |

`local_file.ansible_inventory` writes to `${path.module}/../../ansible/inventory.multipass.ini` (not `inventory.ini`), so this workspace never conflicts with an existing AWS deployment's inventory.

No AMI data source, no security group, no IAM instance profile, no key pair
resource, no VPC/subnet — Multipass has no equivalent objects; the shared
bridge network and host firewall already permit VM-to-VM and host-to-VM
traffic.

## 2. SSH key handling (detail)

- No `tls_private_key`/`aws_key_pair` resources (unlike `keypair.tf`).
- `ssh_public_key_path` variable defaults to `~/.ssh/id_ed25519.pub`, read via
  Terraform's `file()` function and interpolated into the cloud-init template.
- The generated `ansible/inventory.multipass.ini`'s `[all:vars]` sets
  `ansible_ssh_private_key_file={{ ssh_private_key_path }}` (an **absolute
  path** to the user's real private key — not a repo-local copied file, and
  never written into `ansible/` — so nothing sensitive is duplicated on disk).
- If the user prefers RSA or a different key file, both `ssh_public_key_path`
  and `ssh_private_key_path` are plain string variables, overridable in
  `terraform.tfvars`.

## 3. Ansible change needed for Consul scenarios (applied)

Two-line change per file, additive only, does not alter default AWS behavior
— already applied to `consul_servers.yaml`, `consul_clients.yaml`, and
`consul_dns_token.yaml` (§0):

```yaml
# ansible/playbooks/consul_servers.yaml, consul_clients.yaml, consul_dns_token.yaml
vars:
  # was: consul_cloud_auto_join_enabled: true
  consul_cloud_auto_join_enabled: "{{ consul_use_aws_cloud_join | default(true) }}"
```

The Multipass inventory's `[all:vars]` will add one line once `terraform/multipass/inventory.tpl` is written (§1):

```ini
[all:vars]
consul_use_aws_cloud_join=false
```

Inventory group vars are loaded before the play's `vars:` block is
templated, so this resolves correctly to `false` only for
`inventory.multipass.ini` runs, leaving `inventory.ini` (AWS) untouched.

## Open risks / things that must be verified empirically

These can't be fully resolved from reading code — they need a real `terraform apply` to confirm:

1. **Exact cloud-init syntax** the provider's `cloudinit_file` expects for
   appending an SSH key to the default `ubuntu` user (top-level
   `ssh_authorized_keys:` list vs. a full `users:` override). Needs a test run.
2. **IP stability** — Multipass IPs are normally stable per-instance for the
   VM's lifetime, but can change across a delete/recreate cycle. `terraform
   apply` re-runs should be tested for whether the `ipv4` computed attribute
   updates cleanly and whether the regenerated inventory + already-issued TLS
   certs (SAN = old IP) need a re-run of the `tls` role.
3. **Memory headroom** — 4GB per client may be tight once Docker + Nomad +
   a demo job (e.g. Countdash) are all running; may need to bump if OOM is
   observed.
4. **`geerlingguy.docker` galaxy role** on Multipass's Ubuntu image — expected
   to work identically to AWS (same apt-based install), but unverified on
   Multipass specifically.
5. **macOS permission prompts** — first `multipass launch` may trigger a
   system dialog for networking/virtualization permissions; this is a one-time
   manual step, not something Terraform can automate.
