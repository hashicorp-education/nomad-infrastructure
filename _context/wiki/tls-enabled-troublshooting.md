# Troubleshooting: TLS Certificate Bugs Causing Browser Warnings and Consul Leader Election Failure

## Summary

Four related but distinct TLS/mTLS bugs surfaced across one session.
Bugs 1–3 trace back to a single root defect in how the `tls` role generates
leaf certificates (`ansible/roles/tls/tasks/cert_generate.yaml`). Bug 4 was
an unrelated config-drift bug in a later playbook that happened to produce
a symptom (Nomad placement failure) that initially looked cert-related.

1. Browsers showing certificate errors when accessing the Consul/Nomad UIs
   (Chrome and Safari hard-fail, Firefox soft-warns).
2. A regression introduced while fixing #1, which broke Consul/Nomad
   server-to-server mutual TLS (mTLS).
3. Consul failing to elect a Raft leader after a redeploy (`500 (No cluster
   leader)`) even after the certificate fix was verified correct — because
   already-running Consul processes never reloaded the new certs.
4. A Nomad job failing to place with a `${attr.consul.version}` constraint
   error, caused by a later playbook (`consul_dns_token.yaml`) silently
   disabling TLS on Consul client agents, breaking client→server RPC.

This document captures the diagnosis chain, the fixes, and the reasoning, so
future cert or mTLS issues can be triaged faster.

---

## Background: two independent security layers

It is important to keep these two layers separate when troubleshooting:

| Layer | Secures | Mechanism |
|-------|---------|-----------|
| Gossip / Serf (cluster membership, AWS Cloud Auto-Join) | Node discovery and membership | Shared symmetric encryption key |
| `internal_rpc` (Consul) / RPC (Nomad) | Raft consensus, leader election, server-to-server RPC | x509 mTLS using the certs generated by the `tls` role |

A "no cluster leader" error can look like an Auto-Join problem, but Auto-Join
only affects whether nodes discover each other via gossip. If gossip is
healthy (nodes show up in `consul members`) but no leader is ever elected,
the problem is almost always in the mTLS layer used for Raft/RPC, not
Auto-Join.

## Bug 1 — RFC 5280 violation: empty Subject + non-critical SAN

### Symptom

Chrome and Safari refused to load the Consul (`8443`) and Nomad (`4646`) UIs
with a hard certificate error. Firefox loaded the same certs with only a
standard click-through self-signed-CA warning.

### Root cause

The CSR task in `cert_generate.yaml` never set `common_name`, so every leaf
certificate had an **empty Subject**. Per [RFC 5280 §4.2.1.6](https://www.rfc-editor.org/rfc/rfc5280#section-4.2.1.6),
when the Subject is empty, the Subject Alternative Name (SAN) extension
**must** be marked critical. The original task did not set
`subject_alt_name_critical`, so SAN was non-critical.

- Chrome (BoringSSL) and Safari (Apple Security framework) enforce this rule
  strictly — an empty Subject with a non-critical SAN is a hard validation
  failure.
- Firefox (NSS) does not enforce this strictly and only produces the normal
  self-signed-CA warning.

### Fix

Added `common_name: "{{ item['dns'] }}"` to the CSR task, giving every leaf
cert a real Subject. This makes the non-critical SAN spec-compliant (SAN only
needs to be critical when the Subject is empty).

### Verification

Isolated local test playbook run against `localhost` (`ANSIBLE_ROLES_PATH=roles
ansible-playbook -i localhost, <test_playbook>` with `become: false` at the
play level, using a throwaway `tls_path` under `/tmp`), followed by:

```bash
openssl x509 -in test-server-1.pem -noout -subject
# subject=CN=server.global.nomad
openssl verify -CAfile ca.pem test-server-1.pem
# test-server-1.pem: OK
```

## Bug 2 — Self-inflicted mTLS regression: missing `clientAuth` EKU

### Symptom

After fixing Bug 1, browsers were happy — but the cluster no longer worked at
all. This was caught in local testing before it reached the live cluster.

### Root cause

While fixing Bug 1, `extended_key_usage: [serverAuth]` was also added to the
CSR task, reasoning that browsers prefer certs with a properly scoped EKU. This
was a mistake: **presence of the Extended Key Usage extension restricts the
certificate to only the listed purposes.** A `serverAuth`-only cert fails the
"SSL client" purpose check.

Consul's `internal_rpc` and Nomad's RPC layer use **mutual TLS between
servers** — each server is simultaneously a TLS server (accepting RPCs from
peers) and a TLS client (initiating RPCs to peers) for Raft consensus. A cert
that can only prove `serverAuth` cannot complete the client side of that
handshake, so servers can never open outbound RPC connections to each other,
and no leader can ever be elected.

### Diagnosis

```bash
openssl x509 -in test-server-1.pem -noout -purpose | grep -i "SSL client\|SSL server"
# SSL client : No
# SSL server : Yes
```

`SSL client : No` was the exact signal that the EKU was too restrictive for
mTLS use.

### Fix

Added `clientAuth` back into the EKU list. Final, correct CSR task:

```yaml
- name: Create CSR for {{ item['agent-name'] }}
  community.crypto.openssl_csr_pipe:
    privatekey_path: "{{ tls_path }}/{{ item['agent-name'] }}-key.pem"
    common_name: "{{ item['dns'] }}"
    subject_alt_name:
      - "IP:127.0.0.1"
      - "IP:{{ item['ip'] }}"
      - "IP:{{ ansible_host }}"
      - "DNS:localhost"
      - "DNS:{{ item['dns'] }}"
    key_usage:
      - digitalSignature
      - keyEncipherment
    key_usage_critical: true
    extended_key_usage:
      - serverAuth
      - clientAuth
  register: tls_csr
```

### Verification

```bash
openssl x509 -in test-server-1.pem -noout -purpose | grep -i "SSL client\|SSL server"
# SSL client : Yes
# SSL server : Yes
openssl x509 -in test-server-1.pem -noout -subject
# subject=CN=server.global.nomad
openssl verify -CAfile ca.pem test-server-1.pem
# test-server-1.pem: OK
```

### Lesson learned

Adding EKU restrictions to a certificate used for mutual TLS requires
including **every** purpose the cert will actually be used for. An incomplete
EKU list is a subtle regression — it produces no certificate error at all, it
just silently breaks peer-to-peer communication. Whenever a cert is used for
server-to-server mTLS (not just client-to-server), always include both
`serverAuth` and `clientAuth`, and verify with `openssl x509 -purpose`.

## Bug 3 — Stale in-memory certs on already-running processes

### Symptom

Live, deployed cluster: user ran `teardown.yaml` then
`deploy_consul_nomad_sd.yaml`. Consul ACL bootstrap failed with:

```
consul acl bootstrap failed with an unexpected error (rc=1)
... 500 (No cluster leader)
```

The user re-ran `deploy_consul_nomad_sd.yaml` a second time (after Bug 2 was
already fixed and verified locally) and got the **exact same error** — leader
election was still failing even though the cert fix was confirmed correct in
isolation.

### Why the "already fixed" bug still reproduced

Timeline:

1. First `deploy_consul_nomad_sd.yaml` run: certs generated with the
   `serverAuth`-only bug, Consul services started on all 3 servers using
   those broken certs. Leader election failed — expected, given Bug 2.
2. Bug 2 was fixed in `cert_generate.yaml` (added `clientAuth`).
3. Second `deploy_consul_nomad_sd.yaml` run: the `tls` role correctly
   detected the CSR fields changed, re-signed the certs, and copied the new,
   correct cert files to `/etc/consul.d/tls/` (or equivalent) on every node.
4. **But nothing told the already-running Consul processes to reload those
   files.** Go's `crypto/tls` does not hot-reload certificates on file
   change — a running process keeps serving whatever cert it loaded at
   process start until it is restarted (or sent an application-level reload
   signal). The cert-copy tasks in the playbooks had no `notify` wired to a
   restart handler.
5. Result: the files on disk were correct, but every running Consul process
   was still using the original broken (`serverAuth`-only) cert from memory
   — reproducing the identical "No cluster leader" symptom even though the
   underlying fix was verified correct.

### Why this was not an Auto-Join issue

Ruled out early: gossip/serf (which Auto-Join affects) is a separate,
independent security mechanism (symmetric key) from the x509 mTLS used by
`internal_rpc`. Confirming that the certs were the correct shape did not, by
itself, guarantee the *running* processes were using them — that gap is what
this bug is about.

### Diagnosis approach

The general pattern for this class of bug: when a fix is verified correct in
an isolated test but the identical symptom persists on the live system,
the next hypothesis is **not** "the fix is wrong" but **"was the fix actually
loaded by the running system?"** — i.e. is the running process using stale
state (unrestarted service, unreloaded config, cached data) rather than the
newly-corrected artifact on disk.

### Fix

Two parts:

**A. Reactive — unblock the current stuck cluster.** Manually restarted
Consul on all 5 live nodes:

```bash
ansible servers,clients -i inventory.ini \
  -m ansible.builtin.systemd_service -a "name=consul state=restarted" \
  --become
```

All 5 hosts (`nomad-consul-server-1/2/3`, `nomad-consul-client-1/2`) reported
`CHANGED`. Verified a leader was elected afterward via the Consul loopback
HTTP API (no TLS needed since Consul serves plain HTTP on `127.0.0.1:8500`):

```bash
curl -s http://127.0.0.1:8500/v1/status/leader
# "10.0.1.56:8300"
```

**B. Proactive — prevent recurrence for future deploys.** Added `notify`
support to the generic cert-copy task in
[ansible/roles/helper/tasks/file_copy_local.yaml](../../ansible/roles/helper/tasks/file_copy_local.yaml):

```yaml
notify: "{{ item['notify'] | default(omit) }}"
```

And wired `notify: "Restart consul"` / `notify: "Restart nomad"` into every
`helper_file_copy_local` cert-copy item across all four server/client
playbooks:

- [ansible/playbooks/consul_servers.yaml](../../ansible/playbooks/consul_servers.yaml)
- [ansible/playbooks/consul_clients.yaml](../../ansible/playbooks/consul_clients.yaml)
- [ansible/playbooks/nomad_servers.yaml](../../ansible/playbooks/nomad_servers.yaml)
- [ansible/playbooks/nomad_clients.yaml](../../ansible/playbooks/nomad_clients.yaml)

Now, any future cert regeneration (CSR field change, renewal, CA rotation)
that copies a new cert to a node will automatically trigger the existing
`Restart consul` / `Restart nomad` handler (defined in
`ansible/roles/consul/handlers/main.yaml` and
`ansible/roles/nomad/handlers/main.yaml`, both using
`ansible.builtin.systemd_service` with `state: restarted`), instead of
silently leaving the service running on stale in-memory certs.

### Lesson learned

Any Ansible automation that manages TLS certs (or any config) for a
long-running service **must** wire a `notify`/handler restart into the
cert/config-copy task. Ansible's `changed: true` on a file copy only means
"the file on disk changed" — it says nothing about whether the process using
that file has picked up the change. Without an explicit handler, a corrected
file on disk and a broken running process can coexist indefinitely, and every
symptom will look identical to "the fix didn't work."

## Combined diagnostic toolkit for cert/mTLS issues

| Command | Purpose |
|---------|---------|
| `openssl x509 -in <cert> -noout -subject` | Confirm Subject (CN) is set |
| `openssl x509 -in <cert> -noout -text \| grep -A2 "Subject Alternative Name\|Key Usage\|Extended Key Usage"` | Inspect SAN, Key Usage, EKU and their criticality |
| `openssl x509 -in <cert> -noout -purpose \| grep -i "SSL client\|SSL server"` | Definitive check of whether a cert can act as TLS client and/or TLS server — the fastest way to catch an EKU mTLS regression |
| `openssl verify -CAfile ca.pem <cert>` | Confirm the cert chains to the expected CA |
| `curl -s http://127.0.0.1:8500/v1/status/leader` (Consul) | Check Raft leader election without needing TLS client certs (loopback plain HTTP) |
| `consul members` (via `CONSUL_HTTP_ADDR=http://127.0.0.1:8500`) | Confirm gossip membership is healthy, to rule out Auto-Join as the cause |

## Isolated local testing pattern used during this session

To verify `tls` role changes without touching the live cluster, a throwaway
playbook was run directly against `localhost`:

```yaml
- hosts: localhost
  connection: local
  gather_facts: true
  become: false
  vars:
    tls_path: /tmp/tls_test/.tls
    tls_ca_pem_filename: ca.pem
    tls_ca_key_filename: ca-key.pem
    tls_ca_generate: true
    tls_self_signed_generate:
      - agent-name: "test-server-1"
        ip: "10.0.1.99"
        dns: "server.global.nomad"
  roles:
    - tls
```

```bash
ANSIBLE_ROLES_PATH=roles ansible-playbook -i localhost, /tmp/tls_test/test_playbook.yaml
```

Note `become: false` at the play level — `ansible.cfg` sets `become = True`
globally in this project, which would otherwise prompt for a sudo password on
an ad-hoc localhost test run.

## Bug 4 — Consul client TLS disabled by a later playbook, breaking client→server RPC

### Symptom

After the cluster was healthy and ACL-bootstrapped, deploying
`countdash-consul-service-discovery.nomad.hcl` produced a placement failure
on both client nodes:

```
Placement Failures
countdash-api 1 unplaced — Constraint "${attr.consul.version} semver >= 1.8.0" filtered 2 nodes
countdash-web 1 unplaced — Constraint "${attr.consul.version} semver >= 1.8.0" filtered 2 nodes
```

This looked cert-related (same session, same TLS subsystem) but was actually
a **separate, unrelated bug** in a later playbook.

### Diagnosis

1. `nomad node status -verbose <client-id>` showed no `consul.*` attributes
   at all — Nomad's Consul fingerprinter had never successfully run.
2. Nomad's log file (`/var/log/nomad.log`, not journalctl — see log routing
   note below) showed:
   ```
   [WARN] client.fingerprint_mgr.consul: failed to acquire consul self endpoint:
     error="Get \"http://127.0.0.1:8500/v1/agent/self\": context deadline exceeded"
   [ERROR] client: error discovering nomad servers: error="client.consul: unable
     to query Consul datacenters: Unexpected response code: 500 (rpc error making call: EOF)"
   ```
3. A direct `curl --max-time 5 http://127.0.0.1:8500/v1/agent/self` on the
   client node reproduced the identical hang/timeout — this was not
   Nomad-specific, the local Consul agent itself was not responding.
4. `cat /etc/consul.d/consul.hcl` on the client showed **no `addresses {}`
   block, no `tls {}` stanza, and `https = -1`** — TLS was completely
   disabled on the client agent, even though `consul_clients.yaml` (run
   earlier in the same deploy) had correctly set `consul_tls_enabled: true`.
5. Consul's own log (`/var/log/consul/consul.log`) showed the real failure:
   ```
   [WARN]  agent.client: Retrying RPC to server: method=ACL.TokenRead server=10.0.1.212:8300 error="rpc error making call: EOF"
   [ERROR] agent.client.acl: Error resolving token: error="Error communicating with the ACL Datacenter: rpc error making call: EOF"
   [ERROR] agent.http: Request error: method=GET url=/v1/agent/self ... error="Permission denied: token with AccessorID 'primary-dc-down' lacks permission 'agent:read'"
   ```

### Root cause

`ansible/playbooks/consul_dns_token.yaml` has three plays. **Play 3**
("Reconfigure Consul clients with ACL enabled and node-identity tokens") is
run at the end of every `deploy_consul_nomad_sd.yaml` / `deploy_consul_nomad_wi.yaml`
sequence to add the per-node ACL agent token and DNS token to each client's
config. Its `vars:` block explicitly set:

```yaml
consul_acl_enabled: true
consul_tls_enabled: false   # BUG — should be true
```

This re-templated `consul.hcl` on every client with **TLS completely
disabled**, while the Consul **servers** (`consul_servers.yaml`) still ran
with `consul_tls_enabled: true` and mTLS required on `internal_rpc`. A
plaintext client talking `internal_rpc` to a TLS-only server produces
`rpc error making call: EOF` — the server closes the connection as soon as it
receives non-TLS bytes on the RPC port instead of the expected TLS
handshake.

With RPC broken, the client agent could not resolve ACL tokens against the
servers (`ACL.TokenRead` requires an RPC round-trip to the ACL datacenter),
so **every** local HTTP API call — including the purely-local-looking
`/v1/agent/self` — blocked while Consul retried the RPC, then eventually fell
back to a denied "primary-dc-down" pseudo-token and returned 403. Nomad's
Consul fingerprinter treated the slow/failing response as a timeout and never
populated `consul.*` node attributes, so any job with a
`${attr.consul.version}` constraint failed to place.

The comment in the playbook — *"This replaces the previous drop-in
dns-acl.hcl workaround"* — indicates this play predates TLS being enabled by
default in this codebase and was never updated when `consul_tls_enabled: true`
became the project default.

### Fix

Changed Play 3's vars in
[ansible/playbooks/consul_dns_token.yaml](../../ansible/playbooks/consul_dns_token.yaml)
to match `consul_clients.yaml`:

```yaml
consul_acl_enabled: true
consul_tls_enabled: true
consul_port_https: 8443
consul_connect_enabled: false
```

Re-running `consul_dns_token.yaml` against the live cluster re-templated
`consul.hcl` on both clients (`changed`) and the existing `notify: "Restart
consul"` handler on the config-write task fired automatically, restarting
Consul with TLS re-enabled — no manual restart needed this time, unlike Bug 3.

### Verification

```bash
# consul.hcl now shows https = 8443 and RPC calls succeed:
curl -sv --max-time 5 http://127.0.0.1:8500/v1/agent/self
# HTTP/1.1 403 Forbidden (fast, no hang — anonymous token correctly denied)

# Restarted Nomad clients to force re-fingerprinting:
ansible clients -i inventory.ini -m ansible.builtin.systemd_service -a "name=nomad state=restarted" --become

# attr.consul.version now populated:
nomad node status -verbose <client-id> | grep -i consul
# consul.version = 2.0.1

# Job redeploy succeeded with no placement failures:
nomad job run countdash-consul-service-discovery.nomad.hcl
# Deployment completed successfully — countdash-api 1/1, countdash-web 1/1
```

### Lesson learned

When multiple playbooks re-template the **same** config file for the **same**
role at different points in a deploy sequence (here: `consul_clients.yaml`
then later `consul_dns_token.yaml` Play 3, both writing `/etc/consul.d/consul.hcl`
via the `consul` role), every one of those playbooks must be kept in sync on
security-relevant toggles like `consul_tls_enabled`. A later play silently
overwriting an earlier play's correct config is a much harder bug to spot
than a first-time misconfiguration, because the cluster looks healthy right
up until the specific play that regresses it runs. When debugging "was
healthy, now isn't" after a multi-play deploy, diff the actual rendered
config file against what each play in the sequence *should* have produced,
in play order, rather than assuming only the most recently touched files are
suspect.

Also: an RPC-layer TLS mismatch between agents manifests as `rpc error making
call: EOF`, distinct from the certificate-content errors (`x509:` messages)
seen in Bugs 1–2. `EOF` on an RPC call is the signature of "one side is
speaking TLS and the other isn't" — check `consul_tls_enabled` consistency
across every play that touches the same nodes before assuming a cert content
problem.
